前面两页讲的是 Git 是什么，以及该选哪个平台；这页讲的是最实操的部分：怎么创建云仓库、怎么把本地项目绑定上去、怎么用 Git 做同步和备份。

最推荐的新手路径

  1. 先在本地把项目初始化成 Git 仓库。
  2. 先至少做一次本地提交。
  3. 再去 GitHub / Gitee / GitLab / CODING 上创建一个空远端仓库。
  4. 把远端地址绑到本地。
  5. 第一次 push 上去。

创建云仓库时怎么选

  • 仓库名：建议和你的项目目录名接近，方便识别
  • Public / Private：小说项目通常先用 Private
  • README：如果你已经有本地仓库，新建远端时最好别勾“初始化 README”，避免首次推送时多一次合并
  • .gitignore 模板：可以不选，因为 ANH 初始化通常已经给你生成了合适的 .gitignore

命令行最小流程

git init
git add .
git commit -m "初始化项目"

git remote add origin 你的远端地址
git branch -M main
git push -u origin main

VS Code 图形界面流程

  1. 初始化仓库并提交一次。
  2. 点击 Source Control 里的“发布分支”或“Publish Branch”。
  3. 登录对应平台账号。
  4. 选择公开或私有。
  5. 发布完成后，后续就可以用“同步更改”。

两台电脑同步的正确顺序

  1. 电脑 A：写作 → commit → push
  2. 电脑 B：打开项目前先 pull
  3. 电脑 B：继续写 → commit → push
  4. 电脑 A：下次继续前再 pull
最容易出事的不是 Git 本身，而是“在两台电脑都改了，但谁也没先 pull”。只要养成“开写先拉、收工就推”的习惯，绝大多数同步问题都能避免。

HTTPS 还是 SSH

方式 优点 缺点 适合谁
HTTPS 上手简单 可能涉及浏览器登录、Token 新手
SSH 长期使用更顺手 前期要配密钥 长期多设备用户

建议的新手命令模板

# 第一次绑定远端
git remote add origin https://平台地址/用户名/仓库名.git
git branch -M main
git push -u origin main

# 以后日常同步
git pull
git add .
git commit -m "写明本次改动"
git push

git pull 和 git pull --rebase 该怎么选

做法 会发生什么 更适合什么情况
git pull 拉取远端并合并到当前分支 默认首选；团队协作；规范保守；不希望改写历史
git pull --rebase 先拉远端，再把你本地未推送提交重放到后面 个人项目、多设备单人写作、且你明确理解 rebase 影响时

这里我把默认模板改成了普通 git pull。原因很简单：它更保守，也更符合很多团队规范。如果团队文档、仓库规则、代码评审规范明确写了“不准 rebase 公共历史”或“禁止 rebase”，就应当直接遵守，不要自作主张换成 pull --rebase。

如果你是单人项目，主要目标是减少机械性的 pull merge 提交，并且你清楚知道 rebase 会改写提交历史，那么可以自己选择 git pull --rebase。但这不该被表述成通用默认值。更完整的比较见 Git 本体详解。

双远端备份

如果你既想要 GitHub 生态，又想照顾大陆访问，可以给同一个本地仓库挂两个远端：

git remote add origin https://github.com/you/novel.git
git remote add gitee  https://gitee.com/you/novel.git

git push origin main
git push gitee main

常见故障排查

现象 通常原因 先检查什么
push rejected 远端比你新 先 pull 再推
认证失败 密码 / Token / SSH 密钥问题 远端地址类型和登录方式是否一致
首次推送报冲突 远端创建时多初始化了 README 确认远端是不是空仓库
两台电脑互相覆盖 没先 pull 就直接改 建立固定顺序：先拉再写
大文件推不上去 平台容量 / LFS / 仓库限制 先别把大导出文件直接进 Git 历史
如果你只是想把 ANH 初始化出来的项目安全纳入 Git，顺手看一下 工作区初始化文件 和 .gitignore，避免把不该进仓库的缓存也推上去。
