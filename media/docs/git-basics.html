这篇文档讲什么

这一页专门讲 Git 本身，不是讲“哪个网站托管 Git”，也不是讲“VS Code 上哪个按钮对应哪个命令”。如果你已经知道版本管理大概是什么，但还是搞不清 commit、branch、HEAD、stash、tag、remote 这些词到底在说什么，这页就是给你用的。

建议阅读顺序：先看 版本管理是什么 建立大框架，再读这页理解 Git 本体，最后看 Git 与 VS Code 集成 和 云仓库同步与备份 落地操作。

Git 到底是什么

Git 是一个分布式版本控制系统。拆成人话是：

  • 版本控制：它会按顺序记录项目在不同时间点的状态。
  • 分布式：每台电脑上的本地仓库通常都带着完整历史，不是只有云端那一份才叫“真仓库”。
  • 面向差异和历史：它不只是保存“现在这个文件”，更保存“这个项目是怎么一步步变成现在这样的”。

你可以把 Git 想成三样东西叠在一起

1. 工作区 Working Tree
   你正在编辑的真实文件

2. 暂存区 Index / Staging Area
   你准备放进下一次提交的改动清单

3. 仓库 Repository
   已经正式写入历史的提交串

新手最容易卡住的地方，不是命令本身，而是不知道这三层彼此有什么区别。你只要把这三层分清，Git 的大多数日常操作都会突然变得可解释。

图 1：Git 的最小心智模型

编辑文件
  ↓
工作区发生变化
  ↓ git add
暂存区记录“下一次提交要放哪些变化”
  ↓ git commit
仓库里生成一个新的提交
  ↓ git push
把本地提交送去远端

最重要的 10 个词

词 准确但好懂的解释 你在写作里会碰到什么场景
Repository 仓库 一个被 Git 管理的项目，里面有完整提交历史 你的整部小说项目目录
Working Tree 工作区 当前磁盘上的文件内容 你刚改完的正文、设定和资料文件
Index 暂存区 下一次提交准备收进历史的那部分变化 你只想先提交第六章，不想把半成品设定一起交上去
Commit 提交 一次带说明的历史快照 “完成第六章初稿”
Branch 分支 指向某条提交线的名字 开一条“BE 结局试写”分支，不污染主线
HEAD 你当前所在位置的指针，通常指向当前分支的最新提交 决定“你现在正在哪条历史线上工作”
Tag 标签 给某个提交贴一个稳定名字 给“投稿版”“出版版”做里程碑标记
Remote 远端 另一个仓库地址，通常是云上的 GitHub / GitLab / Gitee 仓库 用来同步、备份、跨设备继续写
Merge 合并 把另一条历史线的结果并进来 试写分支满意了，合回主线
Diff 差异 两个状态之间到底改了哪些行 核对这一轮润色到底动了什么

Git 最常见的日常循环

  1. 改文件。
  2. 用 git status 看哪些文件改了。
  3. 用 git diff 看改了什么。
  4. 用 git add 把该交的那部分改动放进暂存区。
  5. 用 git commit -m "说明" 形成一个历史节点。
  6. 需要同步或备份时，再用 git push 发到远端。

为什么 Git 故意设计出“暂存区”这一步

因为现实世界里的改动经常不是一次性干净完成的。你可能同时做了三件事：

  • 修了一章正文里的病句。
  • 顺手改了角色卡里的年龄。
  • 又开了一个半成品的新设定文件。

这时你未必想把三件事打包成一个提交。暂存区的意义，就是让你能说：

“这次提交只交正文病句修订和角色年龄修正，
那份半成品新设定先别进历史。”

保存、提交、推送，这三个动作完全不是一回事

动作 发生在哪 意义
保存 编辑器和磁盘 把当前内容写进文件
提交 Commit 本地 Git 仓库 把一组改动写进本地历史
推送 Push 本地仓库到远端仓库 把本地已有提交同步到云端

一组你真的会每天用到的命令

命令 用途 怎么理解
git status 看仓库当前状态 先别乱按，先看现场
git diff 看工作区和暂存区之间的差异 确认你到底改了哪几行
git diff --cached 看已经暂存、准备提交的那部分差异 提交前最后核对一次
git add 文件名 把改动加入暂存区 告诉 Git“这部分要进下一次提交”
git commit -m "说明" 创建提交 给当前版本拍一张带说明的快照
git log --oneline 简洁查看提交历史 快速回顾过去做过什么
git log --graph --oneline --decorate 看分支图 理解历史线怎么分叉、怎么合并
git switch 分支名 切换分支 换到另一条修改线
git switch -c 新分支名 创建并切换到新分支 准备试新剧情或大改
git push 推送到远端 同步和备份本地提交
git pull 拉取远端并尝试合并到当前分支 更保守，也更符合很多团队默认工作流
git pull --rebase 拉取远端后，把本地未推送提交重放到最新远端后面 更适合理解了历史改写影响、且团队允许这样做的人
git tag v2.0-终稿 给当前提交贴标签 标出“终稿”“投稿版”“出版版”
git tag -a v3.0 -m "出版版" 创建附注标签 比轻量标签更像正式里程碑
git stash 临时把未完成改动收起来 现场太乱，但你得先切去做别的事

图 2：分支到底是什么

main:   A --- B --- C
                 \
experiment:       D --- E

main 代表主线
experiment 代表“试写另一版剧情”
它们最开始共享历史，后来分叉

很多新手以为分支会复制整个项目。不是。分支更像“指向不同提交位置的标签”。它很轻，所以你应该敢于开分支做试验，而不是靠复制文件夹硬分叉。

什么时候该开分支

  • 要尝试另一版剧情走向。
  • 要做一次风险较高的大规模重构。
  • 准备和别人协作，想把某项工作隔离开。
  • 想保留主线稳定可用，但同时试新方案。

什么时候不要滥开分支

  • 只是改几个错字或补几句设定，不必什么都开分支。
  • 如果你根本不会合并，先把单分支提交习惯练稳。
  • 一堆长期不合并的分支只会制造历史垃圾。

远端和本地的关系

你的电脑里有一份本地仓库
GitHub / GitLab / Gitee 里有一份远端仓库

push = 把本地已有提交送过去
pull = 把远端新提交拿下来
clone = 第一次把远端整仓复制到本地

远端不是 Git 的本体，它只是 Git 很常见的一种落地场景。就算完全离线，你照样可以在本地提交、看历史、开分支、打标签。

新手最常犯的 6 个误解

  1. “保存了就等于提交了。” 不是，保存只是写磁盘。
  2. “推送失败说明本地历史没了。” 不是，本地提交通常还在。
  3. “分支很危险，最好别碰。” 恰恰相反，分支是降低风险的工具。
  4. “删除文件就等于历史里也没了。” 不是，旧提交仍然能找回。
  5. “GitHub 就是 Git。” 不是，GitHub 只是 Git 托管平台之一。
  6. “我只写小说，不需要 Git。” 越是长期、反复改稿、跨设备的项目，越适合 Git。

一个适合小说作者的最小纪律

  1. 每次写作前先 git pull 或先确认你已经是最新。
  2. 每次写作结束后至少做一次清晰提交。
  3. 重大修改前先打标签或开分支。
  4. 不要把缓存、临时导出和本地机器专属文件一起提交。
  5. 不要把 Git 当唯一备份，远端和额外归档仍然值得保留。

Git 的内部结构为什么能高效保存历史

Git 并不是每次都傻乎乎地复制整个项目目录。它内部主要围绕几类对象组织数据：

对象 作用
blob 文件内容对象
tree 目录结构对象，记录某层目录里有哪些文件和子目录
commit 记录一次提交，它会指向一个 tree，并指向父提交
ref 给某个提交起名字，比如分支名、标签名
HEAD 当前工作位置，通常指向某个分支 ref

图 3：提交为什么能连成历史

Commit C  -> parent: Commit B
Commit B  -> parent: Commit A
Commit A  -> parent: none

所以 Git 不只是“存快照”，
还知道“这个快照是从哪个上一个快照长出来的”。

为什么说 Branch 只是“一个会移动的名字”

main -> Commit C
HEAD -> main

当你再提交一次：
main -> Commit D
HEAD -> main

分支名本身不是一大坨副本，它只是一个指向最新提交的位置标记。正因为它轻，Git 才鼓励你用分支而不是用复制文件夹来试验。

reset、restore、revert 到底有什么区别

命令 主要影响 适合什么场景 风险感受
git restore 文件名 工作区文件 丢掉尚未提交的某个文件改动 中等，丢的是未提交内容
git restore --staged 文件名 暂存区 把文件从暂存区拿出来，但保留工作区改动 低
git reset --soft HEAD~1 分支指针 想撤回上一次提交，但保留改动和暂存状态 中
git reset --mixed HEAD~1 分支指针和暂存区 想拆掉上一次提交，改动回到工作区 中
git reset --hard HEAD~1 分支指针、暂存区、工作区 明确要直接扔掉未保留的现场 高
git revert HEAD 提交历史 不重写历史，而是新增一个“反向提交”撤销旧提交 更安全，适合已推送历史
git reset HEAD 文件名 暂存区 旧式写法，用来取消暂存 低
简单记法：restore 更像“把文件状态拿回来”，reset 更像“改指针位置”，revert 更像“追加一个反向补丁”。

merge、rebase、cherry-pick 分别在干什么

命令 做的事 什么时候考虑用
git merge 把另一条线整体并进来 功能分支完成后合回主线；团队协作、保留真实分叉历史时优先考虑
git rebase 把一串提交“挪到”另一个基底之后 想让历史更线性，尤其是整理自己尚未共享的本地提交时
git cherry-pick 只挑某一个提交复制到当前分支 只想借一个修复，不想整条分支都并进来

merge 和 rebase 的核心区别

维度 merge rebase
对历史做什么 保留原有分叉，再新增一个合并结果 改写提交的“长相”和位置，让它们像是从新基底直接长出来的
提交 ID 会不会变 通常不会改已有提交 会，新生成的是另一批提交 ID
历史看起来怎样 更真实，能看见什么时候分叉、什么时候合并 更线性，更像一条直线
对协作的影响 更稳妥，尤其适合共享分支和多人协作 如果拿去改已经共享的历史，容易让别人本地历史对不上
为什么有些规范禁用它 一般不会因为安全性被禁 因为它会改写历史。很多团队禁止在公共分支、已推送分支、受保护分支上用它
更适合谁 大多数团队、想保留上下文的人、偏保守流程的人 理解 Git 历史模型、只整理自己本地未共享提交的人

图 4：同一批改动，merge 和 rebase 的结果长什么样

分叉之前：
main:    A --- B --- C
feature:           \
                     D --- E

如果用 merge：
main:    A --- B --- C -------- M
                     \        /
feature:               D --- E

如果用 rebase：
main:    A --- B --- C --- D' --- E'

M 是新的 merge commit
D' E' 不是原来的 D E，而是“重放后生成的新提交”

为什么很多团队更偏向 merge

  • 它不隐瞒历史：谁从哪条分支分出去、什么时候合进来，一眼能看出来。
  • 它不改写公共历史：已经推给别人的提交不会突然换一套 ID。
  • 它更适合审计和回溯：很多团队、很多规范更看重“真实过程可追踪”。
  • 它更符合保护分支策略：很多仓库规则默认就是 PR 合并、保留 merge commit。

为什么有人仍然喜欢 rebase

  • 历史更直：看日志时像单线时间轴。
  • 减少机械性的 pull merge 提交：特别是在单人、多设备切换时。
  • 整理本地提交更方便：尤其是交 PR 前，把自己的一串零碎提交理顺。

什么时候应该优先选 merge

  • 你的团队规范明确禁止 rebase。
  • 你操作的是共享分支、公共分支、受保护分支。
  • 你不希望历史被重写，希望保留真实开发过程。
  • 你对 rebase 的冲突处理和历史改写后果还不够熟。

什么时候 rebase 才相对合理

  • 你整理的是自己本地尚未共享的提交。
  • 这是个人项目或团队明确允许的工作流。
  • 你清楚知道 rebase 后提交 ID 会变，也知道后续该如何 push。
  • 你要的是线性历史，而不是完整保留分叉轨迹。
保守而正确的默认建议：如果你没有非常明确的理由，就先用 merge 思维来理解 Git；如果团队规范说不能 rebase，那就把这条规范当硬约束，而不是“建议”。rebase 不是更高级，它只是另一种会改写历史的整理手段。

图 5：为什么有时候会冲突

你改了第 10 行
别人也改了第 10 行

Git 能自动合并很多“不重叠”的修改，
但面对同一位置的不同改法时，
它不知道你想保留哪一个，于是要求你手工决策。

所以冲突不代表仓库坏了。它只是 Git 在说：“这里我不敢替你做语义决定。”

标签 Tag 在写作项目里特别有用

  • 给投稿版本打标签：投稿版-2026-05
  • 给出版审校前版本打标签：出版前送审版
  • 给重大剧情节点打标签：第三卷重构前
git tag v2.0-终稿
git tag -a v3.0 -m "出版版"
git push origin v2.0-终稿

一个从零到一的 Git 命令行示例

git init
git status
git add .
git commit -m "初始化小说项目"

# 继续写作
git status
git diff
git add chapters/第06章.md
git add novel-helper/roles.md
git commit -m "完成第六章初稿并补齐角色设定"

# 打一个里程碑标签
git tag -a v0.6 -m "第六章完成"

# 绑定远端并推送
git remote add origin 远端地址
git push -u origin main

如果你把现场搞乱了，先问自己哪一类问题

  1. 只是工作区乱了？ 先看 git status 和 git diff。
  2. 只是暂存错了？ 优先想 git restore --staged。
  3. 提交说明写错或提早提交了？ 先考虑 git commit --amend 或软重置。
  4. 已经推到远端了？ 优先想 git revert，不要直接改公共历史。
  5. 只是想先把未完成工作挪开？ 先想 git stash。

新手应避免的高风险习惯

  • 没看清状态就直接乱用 reset --hard。
  • 把几十件不相关的修改塞进一个提交。
  • 在公共分支上反复改写历史，再强推覆盖别人。
  • 把缓存、导出成品、构建产物、私密信息一起提交。
  • 完全不写提交说明，最后历史只剩“update”或“修改”。

一张给小说作者的 Git 速查表

git status                # 先看现场
git diff                  # 看还没暂存的改动
git diff --cached         # 看准备提交的改动
git add 文件名             # 暂存指定文件
git restore --staged 文件名 # 取消暂存
git commit -m "说明"       # 创建提交
git log --oneline         # 看简洁历史
git log --graph --oneline # 看分支图
git switch 分支名          # 切分支
git switch -c 新分支名      # 新建并切换分支
git stash                 # 临时收起现场
git tag v2.0-终稿         # 打标签
git revert HEAD           # 用新提交撤销最近一次提交
