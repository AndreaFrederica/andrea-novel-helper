这一组文档在解决什么问题

Git 以前零散地挂在 VS Code 基础、核心概念和高级功能里，用户很难判断“我现在到底该先学概念、先学按钮，还是先学同步”。现在把它单独做成一个大类，按学习顺序组织。

建议阅读顺序

  1. 版本管理是什么：先建立为什么要有提交、历史、回滚、分支。
  2. Git 本体详解：把 add、commit、branch、merge、rebase、stash 这些机制弄明白。
  3. VS Code Source Control：看这些概念在 VS Code 原生界面里对应哪些按钮。
  4. Git 与 VS Code 集成：看 ANH 项目里实际怎么把 Git 工作流落地。
  5. 云仓库同步与备份：处理多设备同步、远端仓库和备份。
  6. Git 托管平台比较：选 GitHub、GitLab、Gitee、Codeberg、CODING 等平台。
  7. .gitignore：知道哪些文件应该进仓库，哪些不应该。

最少先会哪几件事

  • 看改动。
  • 写提交。
  • 把仓库推到远端。
  • 在出错时知道优先看 diff 和历史，而不是直接覆盖文件。

对写作者尤其重要的点

  • Git 不是程序员专属工具，它本质上是你的写作历史保险箱。
  • 同步不等于备份，真正可靠的同步一定包含提交历史和远端仓库。
  • UI 按钮背后仍然是 Git 机制，所以学一点本体概念能大幅减少误操作。

为什么要把 Git 从旧分类里拆出来

因为 Git 不是 VS Code 的一个小子功能，也不是“高级用户才需要”的附属项。它至少横跨三层：

  • 概念层：什么是版本、分支、提交、回滚。
  • 工具层：Git 命令行和仓库模型。
  • 界面层：VS Code Source Control、Graph、Timeline、Merge Editor。

如果把这三层继续拆散，新手会以为“我只需要会点提交按钮”，结果一遇到冲突、误删、同步错乱就完全失控。

对 ANH 项目的推荐工作流

  1. 项目初始化完成后尽快建仓库。
  2. 把角色、正文、配置的关键里程碑做成清晰提交。
  3. 在重要重构前先提交一次，而不是指望撤销键。
  4. 跨设备写作时养成先 pull、再写、再 commit、再 push 的节奏。
  5. 把 novel-helper 里的项目数据和正文一起纳入同一个版本流。
如果你其实已经会 Git 命令，只是不熟 VS Code 面板，直接跳到 VS Code Source Control；如果你最关心的是“我该怎么在两台电脑之间同步小说工程”，直接跳到 云仓库同步与备份。
