这一页讲什么

这页讲 VS Code 自带的 Git / 源代码管理界面。即使你不想背命令，也应该知道怎么在 VS Code 里看改动、暂存、提交、同步和处理冲突。

前提：VS Code 的 Git 不是自己实现的 Git

官方 Source Control 文档一开始就强调：VS Code 依赖你机器上安装的 Git。也就是说：

  • 你需要先安装 Git。
  • 提交时 Git 会使用你配置的用户名和邮箱。
  • VS Code 是 Git 的图形界面入口，不是替代 Git 本体。

怎么打开源代码管理视图

  • 活动栏点击分支图标
  • Ctrl+Shift+G

你会在这里看到什么

  • Changes：已修改但未暂存的文件。
  • Staged Changes：已暂存、准备进入下一次提交的文件。
  • 提交输入框：写提交说明。
  • 同步按钮：和远端同步。
  • 图形历史 Graph：看提交历史和分支结构。
图上英文对照：Source Control = 源代码管理；Repositories = 仓库；Changes = 未暂存改动；Staged Changes = 已暂存改动；Commit = 提交；右侧红绿 diff = 删除 / 新增内容。

最基本的 Git 流程

  1. 修改文件。
  2. 打开源代码管理视图。
  3. 点开文件看差异。
  4. 确认没问题后暂存。
  5. 输入提交说明。
  6. 点击提交。
  7. 需要时再同步远端。

对写作项目来说，最重要的不是炫技，而是稳定形成“改完就提交”的习惯。

怎么看差异

在源代码管理里点某个文件，会打开差异视图：

  • 左边：旧版本。
  • 右边：新版本。
  • 颜色块：标明新增、修改、删除。

提交前先看差异是极重要的习惯。很多误删、误改、误格式化都能在这里第一时间发现。

暂存是什么意思

暂存就是把文件放进“下一次提交的候选清单”。它不是提交，也不是上传，只是“先放到待提交篮子里”。

  • 文件旁边的 +：暂存单个文件。
  • Changes 标题旁的按钮：暂存全部。

如果你只想提交这次和“第一章定稿”有关的改动，就只暂存那些相关文件。

提交说明怎么写

提交说明要描述“这次干了什么”，而不是写情绪或流水账。

  • 好例子：补第一章冲突段落；重构角色设定目录；修正文案里的称谓不一致。
  • 差例子：改了一下；提交；测试。

同步远端是什么

当你的仓库关联了 GitHub、GitLab、Gitee 等远端后，VS Code 会在状态栏显示入站/出站提交。你可以：

  • Fetch：只看远端变化。
  • Pull：把远端更新拉到本地。
  • Push：把本地提交推到远端。
  • Sync：通常是 pull + push 的快捷入口。

Source Control Interface 的几个关键部件

官方文档把内建 Git 界面分成几块：

  • Source Control view：中心操作台。
  • Diff editor：对比文件版本。
  • Source Control Graph：看提交图。
  • Gutter indicators / blame：编辑器内局部提示。

按范围暂存，而不是总是整文件暂存

官方明确提到：你可以在 diff 里只暂存选中的一段。这对“一个文件里混了两类改动”的场景很重要。

例如同一份文档里你既修了错字，又改了一个章节结构。如果它们应该拆成两个提交，可以直接在差异里按范围暂存。

Graph 和 Timeline 的分工

  • Graph：看整个仓库的提交历史和分支关系。
  • Timeline：看某个文件自己的历史。

Graph 适合回答“这个项目最近发生了什么”；Timeline 适合回答“这份文档什么时候被谁改过”。

图上英文对照：Graph = 提交图；Incoming Changes = 传入变更；Repositories = 仓库列表；main / upstream/main = 本地分支 / 远端分支；Auto = 自动跟随图视图。

分支、stash、worktree

官方 Source Control 文档已经把这些都纳入 VS Code 工作流：

  • Branch：并行做不同任务。
  • Stash：临时收起未完成改动。
  • Worktree：同一仓库开多个工作目录并行工作。

对写作用户来说，最常用的是分支：比如“出版修订版”和“网络连载版”分开处理。

冲突处理

官方文档提到，VS Code 在冲突时会给出：

  • 内联冲突按钮：Accept Current / Accept Incoming / Accept Both。
  • 3-way Merge Editor：三方合并视图。
  • 源代码管理视图中的冲突文件高亮。

处理冲突时，最忌讳“看到冲突标记就随手全删”。先理解三份内容分别代表什么，再决定保留哪一部分。

Git 输出和 blame

官方建议初学者善用 Git 输出：

  • Show Git Output：看 VS Code 背后到底执行了哪些 Git 命令。
  • Git blame：查看当前行最近是谁在什么时候改的。

当你怀疑“为什么 VS Code 的 Git 行为和我手敲命令不一样”时，先看 Git Output，通常很快就能对上。
